# Phase 35 — Irreversible Loan Deletion With Audit Trail

## Goal

Let an admin delete any **active** pagaré, with or without payments, mainly so test/fictitious pagarés can be removed. The pagaré must not truly vanish: it stays in the database as a record that it existed, its money movements are reversed through the same auditable mechanism voiding a payment already uses, and anyone in the panel can still look it up read-only. Deleting is **permanent** — there is no restore, in the api or the panel.

Supersedes `docs/phases/PHASE_30_LOAN_CORRECTION.md`'s "only while it has no payments" rule.

## Resolved — confirmed directly with the human (2026-11-05)

1. **Why:** the client creates test/fictitious pagarés to try things out (usually with very high numbers they never use for real ones) and needs to remove them afterwards.
2. **Who:** **admin only** (`@Roles(UserRole.Admin)`). Today `DELETE /loans/:id` is `@RequireModule(AppModule.Loans)`, which also lets a collector with the loans module delete — Phase 30's brief said admin-only, the code drifted. This phase makes it admin-only for real. **Viewing** deleted pagarés is open to every authenticated user (admin and collector), same as every other loan read today, so a collector can answer a client who asks about one.
3. **Soft and irreversible:** soft delete (rows stay, `deleted_at` set). No restore endpoint, no restore button — "si le dan a borrar, no se puede deshacer y punto."
4. **Which statuses:**
   - `active` — yes, with or without payments.
   - `paid` — no.
   - `refinanced` — never on its own. Deleting an active pagaré that came from a refinance deletes the **whole chain** behind it (every earlier loan reachable through `refinanced_from_loan_id`). It never revives the earlier loan: reactivating its cancelled cuotas would change the client's real debt (with mora accrued since their original due dates) without notifying them. A real refinance done wrong is still fixed with a new refinance, which does notify.
5. **Payments are voided, not left behind.** Every non-voided payment of every deleted loan is voided with the same logic as `InstallmentsService.voidPayment` (`void_reason = 'Pagaré eliminado: <motivo>'`), so the money stops counting everywhere (monthly "pagos recibidos" sums payments by date alone, regardless of the loan — a payment left un-voided would keep counting fake money as collected).
6. **Saldo a favor:** corrected only through append-only ledger entries, never by editing or deleting existing ones (what an auditor expects):
   - a payment that **spent** credit → `restored` entry, the credit goes back to the client;
   - a payment that **generated** credit → `reversed` entry, the credit is taken back.
   - **Blocks** (option "a", confirmed) when credit generated by one of these payments was already spent on another pagaré's cuota or refunded in cash — the same rule `reverseCreditGeneratedBy` already enforces. The error names exactly which payment used it (cuota N of pagaré #X) so the admin voids that one first. Never cascades into a real pagaré automatically, never leaves a negative balance.
7. **Promissory note number:**
   - deleted loan **without** payments → its number is free again (today's behavior);
   - deleted loan **with** payments (voided ones count) → its number stays reserved forever.
   - `getNextPromissoryNoteNumber` ignores deleted loans (today it counts them, so a deleted test pagaré `#9999` keeps the suggestion at `#10000` forever).
8. **Mora is frozen at deletion.** A snapshot of every cuota (amount, capital, due date, status, days overdue, mora, paid, total) is stored at the moment of deletion, so the read-only view shows exactly what the app showed then and never keeps accruing.
9. **Double confirmation** (panel) with a **mandatory reason** and the **pagaré number typed** to confirm. The api re-checks both: the reason is non-empty and the typed number matches.
   - The typed number is compared with the loan's **current** `promissory_note_number`, read inside the deletion transaction. Renumbering (`PATCH /loans/:id/promissory-note-number`) overwrites that column in place (the old number only survives in the audit log), so there is no old number to be asked for — on a renumbered chain the admin types the one current number of the active pagaré.
   - Compared leniently on format only: surrounding spaces ignored and a leading `#` optional on either side (legacy rows like `743` have none). Never a partial or different number.
   - A mismatch caused by a renumber since the preview was opened is rejected (nothing deleted) with the current number in the message: "El número de este pagaré cambió a #1201. Cierra y vuelve a intentarlo."
10. **Where deleted pagarés appear:** an "Eliminados" tab in Préstamos, a read-only detail page, and the client's profile loan list (with an "Eliminado" badge). They never count toward any client figure (loans count, amount lent, cupo, debt) nor any dashboard/report figure, and no WhatsApp message of any kind ever goes out for them.

## Scope

### Data model (migration `AddDeletionAuditToLoans1791900000000`)
- [x] `loans.deleted_by_user_id` — UUID, nullable, FK → `users.id`, `ON DELETE SET NULL` (same as `audit_logs.actor_user_id`).
- [x] `loans.deletion_reason` — TEXT, nullable. Non-null exactly when the loan was deleted through this flow.
- [x] `loans.deletion_snapshot` — JSONB, nullable. The frozen cuotas (see point 8).
- [x] Loans deleted before this phase (no payments, Phase 30) keep these null; the read-only view handles that ("sin motivo registrado", no snapshot → plain installment rows).

### Service and API
- [x] `GET /loans/:id/deletion-preview` — admin only. Read-only: the loans that would be deleted (chain), cuotas count, payments count and total, credit to restore, credit to take back, and blockers (status not active; credit already spent/refunded, naming the payment). Drives the panel's step 1.
- [x] `DELETE /loans/:id` — admin only. Body: `{ reason, confirmPromissoryNoteNumber }`. One transaction: re-run the preview's checks (409/400 on any blocker), store snapshot + `deleted_by_user_id` + `deletion_reason` on every loan of the chain, void every payment (credit entries included), soft-delete installments and loans. `@Audit('loan.delete')`, label includes the reason.
- [x] Number rules (point 7): `assertPromissoryNoteNumberIsUnique` also rejects a number held by a deleted loan that had payments; `getNextPromissoryNoteNumber` ignores deleted loans.
- [x] `GET /loans/deleted` — the "Eliminados" list (number, client, deleted at, deleted by, reason, had payments), filterable by `clientId`/`search`, newest deletion first. Any authenticated user. One row per deleted refinance chain (its active head, with `refinancedLoans` = the earlier loans, newest first; `hadPayments` covers the whole chain; search matches any loan of the chain). *(Changed during implementation from `GET /loans?deleted=true`: its own route and response shape instead of overloading the live list.)*
- [x] `GET /loans/deleted/:id` — read-only detail (any authenticated user): deleted by/at/reason, the frozen cuotas (`hasFrozenFigures: false` and no mora for a pre-Phase 35 deletion), its voided payments with receipts, the other loans deleted with it, and its origination terms (`originationTerms`, same as `GET /loans/:id/origination-terms` — whole chain, refinance mora waiver included — read withDeleted via `LoansService.getDeletedLoanOriginationTerms`). *(Changed during implementation: `GET /loans/:id` keeps returning 404 for a deleted loan, so no live screen or flow can ever receive one by accident.)*
- [x] Client profile: the panel reads its deleted loans from `GET /loans/deleted?clientId=…`; every client figure keeps excluding them.

### Verify (no change expected, must be confirmed with a test or a read of each query)
- [x] Every reminder/notice family (overdue, upcoming, new loan, payment confirmation, Datacrédito) skips deleted loans.
- [x] Dashboard, overdue report, client debt summary and cupo exclude deleted loans and voided payments.

### Tests (mandatory)
- [x] Active loan without payments: deleted, number freed.
- [x] Active loan with payments: payments voided with the reason, number reserved, snapshot stored with frozen mora.
- [x] Refinance chain: every loan in the chain deleted, nothing revived.
- [x] Paid loan, refinanced loan on its own: rejected.
- [x] Credit spent by a payment → restored; credit generated → reversed; generated credit already spent elsewhere → rejected, naming the payment, nothing changed.
- [x] Missing reason / mismatched number → rejected. Non-admin → 403 (enforced by the global `RolesGuard` from `@Roles(UserRole.Admin)`, same as every other admin-only route — not unit tested per endpoint).
- [x] Renumbered loan (and renumbered chain): deleted with its current number; its previous number is rejected; `743` vs `#743` and surrounding spaces accepted.
- [x] `getNextPromissoryNoteNumber` ignores deleted loans.

### Swagger
- [x] Both endpoints documented, including the irreversibility, the chain rule and the blocking rule.

## Definition of done for this phase

- An admin can permanently delete an active pagaré (and its refinance chain), seeing beforehand exactly what will happen to its payments and the client's saldo a favor.
- Deleted pagarés are fully visible read-only to every user, with who, when, why and their frozen figures — no database access needed to answer "what happened to this pagaré".
- All items in `docs/DEFINITION_OF_DONE.md` pass.
